Linux 6.8 · 自定义调度类 · 缓存感知

Yat-CAShed

一个运行在真实 Linux 内核里的 缓存感知调度类（SCHED_YAT_CASCHED）： 用 AJLR 的「收益 / 影响」模型决定任务该放到哪颗核， 并把决策真正接到内核唯一的跨核选核钩子 select_task_rq 上。 仓库同时包含内核补丁、可复现的 QEMU 对比测试，以及一个 Java 调度模拟器。

GitHub 仓库 操作手册 架构说明 改进路线

它解决什么问题

CFS 只关心公平与吞吐，不知道任务上次跑在哪个核、那部分缓存还在不在。

缓存亲和性

按 (任务, CPU) 的历史执行区间估计 recency，计算「留在原核的收益」与「迁到目标核的影响」，取最优。

决策必须被执行

算法只写 debugfs 数字没有意义。选核结果写回 assigned_cpu，并在 pick_next_task 中生效。

可观测

6 个 tracepoint + 4 个 debugfs 节点 + 27 项 per-CPU 计数器，覆盖「进类 → 唤醒 → 选核 → 放置 → 执行」整条链路。

可复现

同一份内核、同一份 initramfs、同一份负载，两个独立 QEMU 进程只改调度策略，自动落 CSV。

实测结果（8 任务 / 4 核 / 2M 迭代 / 200µs 唤醒）

结论要分两层看：「AJLR 已真实接管选核」有数据支撑（唤醒数 → 决策数 → 放置数 → 命中率四者自洽）； 但「性能优于 CFS」不成立 —— 当前实现慢约 2 倍。 原因是 O(nr_cpus²) 的 recency 扫描、每次 O(n) 的 pick 扫描，以及 TCG 模拟放大的切换成本。 一次「按需抢占」的优化经 3 次重复取中位数后被数据否决并已回退，记录在路线图的 A8.2 节。

决策链路

每一跳都有对应计数器，挂死时能定位到具体是哪一跳断了。

→
try_to_wake_up唤醒走到哪
→

→

快速开始

完整步骤（含环境依赖与故障排查）见操作手册。

# 0) 最快的语法检查（只编调度器目标文件）
make kernel-obj

# 1) 编译内核
make kernel-build            # 产物：linux-6.8-main/arch/x86/boot/bzImage

# 2) 验证 AJLR 是否真的接管选核
#    --affinity none 与 --sleep-us > 0 缺一不可，否则测不到
linux-6.8-main/yat_test_scripts/compare_cfs_vs_yat.sh \
    --tasks 8 --iters 2000000 --affinity none --sleep-us 200 --timeout 300

# 3) 提交前门禁（仓库健康 + 文档链接 + 命名 + 符号 + 补丁 + 模拟器）
make verify-all
两个最容易踩的坑：默认的 --affinity shared 会把任务 pin 到单核， 使 select_task_rq 根本不调用调度类；QEMU 启动时加 acpi=off 会让 guest 只剩 1 个 CPU，任何跨核对比都会失真。
